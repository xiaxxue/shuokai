# “说开”体验重构 HTML 原型

这是方向验证用的移动端原型，不是正式客户端实现。它们与 `miniapp/` 完全隔离，不连接真实账号、房间、API、录音或业务数据。

## 快速查看

- 打开 `index.html` 比较两套方向。
- 直接打开 `direction-a/index.html`：安静的私人准备室。
- 直接打开 `direction-b/index.html`：两条互不窥视的路径。
- 每套原型右上角都有“流程 / 全流程”入口，可以跳到全部核心页面、异常与恢复状态。
- URL 支持 `?screen=<状态>`，例如 `direction-a/index.html?screen=common`。
- 对话化主流程截图见 `screenshots/direction-a-guided-dialogue.png` 与 `screenshots/direction-b-guided-dialogue.png`。

建议用 390×844 移动端视口体验，也可以直接在微信内置浏览器或移动 H5 浏览器中打开本地静态文件。

## 方向 A：安静的私人准备室

- 设计隐喻：用户先坐在一张只属于自己的纸桌前；批准后才把一页放到共同桌面。
- 适用用户：第一次使用、情绪混乱、不想先理解方法与流程的人。
- 主要优势：进入门槛低；用户像在对 AI 讲述而不是填表；AI 先复述、再一次一问；私人边界直观。
- 主要风险：双人异步全貌不持续占据视觉中心；复杂进度需要通过状态入口查看。
- 记忆点：纸张、封签与“私人 / 候选 / 已确认”三层内容质感。

## 方向 B：两条互不窥视的路径

- 设计隐喻：双方在两条封闭路径上分别准备；中间的门只有两边当前版本都批准才打开。
- 适用用户：被邀请者，以及对隐私、对称权利和状态透明特别敏感的人。
- 主要优势：持续看清双方各自状态、谁需要行动、为什么共同桌面还没有打开。
- 主要风险：路线与状态更显性，高情绪负荷下可能被感知为需要完成的流程。
- 记忆点：顶部双轨、中央封闭门，以及版本汇合前检查。

## 推荐结论

以方向 A 作为正式体验骨架，吸收方向 B 的双人进度轨、汇合前版本检查和“门重新关闭”反馈。

理由：产品第一任务是帮助用户开始说，而不是先理解流程。A 更能容纳杂乱与迟疑；B 最适合作为邀请、等待、内容变更与双方确认阶段的状态组件，而不是贯穿每个私人编辑页面。

## 覆盖清单

两套原型都可点击访问：

- 首次进入与产品边界
- 温和目标 / 开场
- AI 自然开场与语音/文字分段讲述
- AI 复述确认、用户纠正、继续讲、让 AI 先别问
- 转写加载与失败
- AI 一次一个追问、提问理由、自述回答与跳过
- 用户主动结束讲述、原对话回看、候选整理、逐句取舍与撤销
- 本人批准、分享范围、批准与邀请拆分
- 邀请预览与发送前确认
- 被邀请者安全说明、加入、稍后、拒绝
- 等待、双方独立进度、离开恢复
- 共同点、差异、未核实、边界与分别确认
- 内容变更后的旧确认失效与重新确认
- 七天实验候选、分别同意、进行中、提前停止与复盘
- 网络中断、AI 失败、重复提交、邀请失效、权限不足、对方未响应与暂停

## 原型交互约定

- 顶部文字状态始终说明当前两方可见范围，不只依赖颜色。
- 底部主按钮推进核心演示；次级按钮展示返回、稍后、拒绝和恢复路径。
- “流程 / 全流程”弹层提供所有状态的可直接访问入口；支持 `Escape` 关闭并把焦点返回触发按钮。
- 所有按钮触控高度至少 44px；焦点可见；状态更新区域使用 `aria-live`。
- 使用 `prefers-reduced-motion` 时关闭页面转场与平滑滚动。
- 原型中的姓名、日期、房间状态和正文都是虚构示例。

## 与正式实现的主要差异

- 私人准备的主界面是用户与 AI 的连续对话，不是长文本框或“观察、感受、需要、请求”四张表；四步只作为 AI 的内部提问策略，不能变成必答字段。
- AI 先听完一段、复述目前理解并让用户纠正，再根据刚才的话只追问一件事；用户可继续讲、跳过或让 AI 先别问。
- 只有用户主动说“讲得差不多了，帮我整理”，产品才从对话切换为可编辑候选文稿。
- 不再把 `AI Agent`、`理解层`、内部状态或 Supabase 实现术语作为主界面语言。
- “批准内容”和“发送邀请”成为两个独立动作。
- 被邀请者在加入前拥有安全说明、稍后和拒绝；加入后使用完全对称的私人流程。
- 共同理解按共同、不同、未核实和边界组织，并绑定双方已批准内容版本。
- 任一已批准内容修改后，旧的共同理解确认与实验同意失效。
- 七天实验不再只有接受：双方均可提出修改、不参加、提前停止和独立复盘。

## 需要实现团队注意

- HTML 原型只验证信息架构、文案、视觉方向和交互状态，不定义 API 返回结构。
- 正式实现应复用 uni-app 跨端组件，不直接把 HTML DOM 或 CSS `clip-path` 原样搬入微信小程序。
- 方向 B 的双轨可用普通 `view`、border 与 grid/flex 复现；不要依赖 H5 特有的滤镜或遮罩完成关键信息。
- 状态推进、角色、批准、邀请和版本校验必须继续由 RLS 与受控 RPC 执行；模型不控制授权。
- 详细产品定义、状态模型、AI 契约、指标与待决策项见 `product-definition.md`。

## 验证范围

原型交付应完成以下本地验证：

1. HTML 可由浏览器直接打开，无网络依赖。
2. 390×844、320×568、430×932 视口下核心文案和按钮可访问。
3. 核心流程与全部异常入口可点击，浏览器控制台无错误。
4. 键盘可打开/关闭流程弹层并看见焦点。
5. 页面不包含真实密钥、Token、业务数据或生产配置。
6. `git diff --check` 通过，正式 `miniapp/` 无修改。
