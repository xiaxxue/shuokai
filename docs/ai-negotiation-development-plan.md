# 「说开」AI 协商开发计划

版本：v0.2

依赖：[AI 协商产品规格](./ai-negotiation-product-spec.md)

技术设计：[AI 协商技术设计](./ai-negotiation-technical-design.md)

当前阶段：M2 单方表达纵切正在功能分支实现；migration 尚未应用到测试或生产数据库

## 1. 当前实现基线

仓库已经具备：

- 双人房间、邀请、角色和基础房间状态；
- H5 Supabase 登录及微信平台身份接入；
- 本机私人草稿恢复；
- 非暴力沟通四步编辑：观察、感受、需要、请求；
- 已确认观点、共同视图和行动约定的演示流程；
- Supabase RLS 基础和测试环境部署流程。

当前仍未具备：

- 真实模型调用；
- 四条表达路径及路径推荐；
- 输入、确认和 AI 结果的不可变版本绑定；
- 真实共识 Agent 与审查 Agent；
- 暂停、恢复、撤回和生成失败的完整服务端状态；
- 多 Agent 离线评测与成本、延迟基线。

现有 `Perspective` 技术字段仍是 `fact / meaning / impact / request`，界面已将后两项呈现为 NVC 的“感受 / 需要”。进入 schema 设计时必须消除这个语义错位，不能继续让模型和数据库对同一字段使用不同含义。

## 2. 实施原则

1. 先完成一个真实端到端纵切，不批量制作没有模型和状态支撑的演示页面。
2. 用户确认、权限、版本失效和安全阻断由程序强制执行，不交给模型自行遵守。
3. 每个模型阶段都先有固定结构化模板作为可用降级路径。
4. 每一里程碑必须同时交付行为、测试和可观察的失败状态。
5. schema、RLS 或数据保留发生变化前单独提交设计评审，不直接修改线上数据库。
6. 不做生产部署；测试环境只从已经推送的 GitHub `main` 干净检出部署。

## 3. 里程碑

### M0：产品规格冻结

目标：把产品机制变成开发和测试可以共同引用的合同。

交付：

- 产品目标、范围和非目标；
- 四条表达路径；
- 三类 Agent 与程序边界；
- 页面状态、确认文案和退出行为；
- 产品级状态机；
- 安全、失败和降级规则；
- MVP 验收标准。

完成条件：

- 产品、设计和工程对“理解不等于同意”“路径由用户决定”“暂停优先”没有歧义；
- 每一个页面动作都有后续状态；
- 每一个模型失败都有用户可继续的路径；
- 尚需技术设计的 schema 问题被明确列出而没有偷偷实现。

### M1：技术设计与 schema 评审

目标：确定支持不可变版本、确认和异步模型任务的最小数据结构。

设计内容：

- 表达路径及每条路径的结构化 payload；
- 私人输入、可分享版本和确认记录；
- 共同理解候选、行动候选和双方确认；
- 暂停、撤回、退出、恢复和终态；
- 模型任务的 `job_id / attempt_id / parent_attempt_id`；
- `participant_version_a + participant_version_b + pipeline_version` 绑定；
- 候选内容 hash 与确认绑定；
- 幂等键、唯一约束、状态比较更新和并发冲突；
- RLS 读取、写入和服务端执行边界；
- 数据保留、日志脱敏和删除策略；
- 现有 `Perspective` 字段的语义迁移方案。

必须先评审的 schema 变化：

- 是否新增不可变表达版本表；
- 是否新增模型任务和候选结果表；
- 是否扩展房间状态或拆分房间状态与任务状态；
- 如何迁移现有 `fact / meaning / impact / request` 数据。

完成条件：

- 有状态图、表关系、字段权限矩阵和迁移/回滚方案；
- 对每个参与者证明无法读取对方未确认内容；
- 对重复请求、迟到结果和双方并发给出确定性处理；
- 经明确批准后才创建 migration。

### M2：单方表达纵切

目标：一个参与者可以使用真实或可替换的模型适配层，完成从原始表达到账户确认版本的全过程。

开发内容：

- 房间说明和隐私提示；
- 四路径选择器；
- 轻量路径推荐器；
- 四条路径的编辑器与手动模板；
- 理解 Agent 结构化输入输出；
- 原文、候选稿、待确认点和分享预览；
- 修改、重新整理、确认分享；
- 本机草稿与服务端确认版本分离；
- 超时、格式错误和手动降级；
- 在原始表达和候选结果阶段执行安全检查。

测试重点：

- 四条路径各自的字段约束；
- 推荐失败仍可手选；
- 切换路径不误传旧字段；
- 私人草稿不会出现在快照、日志或对方请求中；
- 确认绑定准确版本，编辑后失效；
- H5 与 mp-weixin 行为一致。

完成条件：

- 用户可以不用 AI 手动完成同一结构；
- AI 输出失败不会丢失原输入；
- 分享按钮展示准确影响和分享内容；
- 模拟 AI 文案不再冒充真实 AI 成功结果。

### M3：双方汇合与理解层共识

目标：双方确认后生成可追溯、可审查、可拒绝的共同理解。

开发内容：

- 双方异步等待和最小进度状态；
- 共识 Agent 理解层调用；
- 共同点、分歧、未核实事实、边界和核心问题；
- 审查 Agent 结构化问题；
- 最多一次语义修订；
- 双方分别确认、标记不准确、退回修改或暂停；
- 任一输入变化使下游结果失效；
- 失败时并列展示双方已确认表达，不展示半成品。

测试重点：

- 双方使用不同表达路径；
- 一方主张事实、另一方否认；
- 一方声明边界；
- 一方修改或撤回时的下游失效；
- 同时确认、重复请求、乱序结果；
- 审查两次失败后的明确停止。

完成条件：

- 共识结果的每个关键结论能定位到稳定的确认字段；
- 任何一方不同意时不会进入行动层；
- 页面明确区分“确认准确”和“同意对方”；
- 一方暂停后不会继续调用共识或通知其具体风险判断。

### M4：行动选项与完成状态

目标：在双方确认共同理解后，生成可调整、可退出的下一步方案。

开发内容：

- 二至三个行动候选；
- 范围、责任方、时间、复盘和退出条件；
- 行动候选审查；
- 双方选择、修改、拒绝或暂不行动；
- 达成行动、保留分歧、共同暂停和单方结束的完成页；
- 房间恢复、过期与关闭规则。

完成条件：

- 行动选项不超出双方确认内容和边界；
- 用户可以不选择任何方案而正常结束；
- 一方修改行动候选后，另一方必须确认同一个准确版本；
- 完成页不把保留分歧显示为失败。

### M5：离线评测与模型选择

目标：证明多 Agent 方案相对固定模板和单 Agent 的收益足以覆盖成本与复杂度。

对照组：

1. 固定结构化模板，不调用生成模型；
2. 单 Agent 完成整理、共识和自检；
3. 理解、共识、审查三类 Agent 流水线。

数据集覆盖：

- 普通误解；
- 事实争议；
- 边界和拒绝；
- 一方暂停；
- 价值冲突；
- 双方路径不同；
- 控制、威胁和潜在伤害；
- 极短、极长、矛盾输入；
- 提示注入和要求泄露对方内容。

主指标：

- 语义保真；
- 严重遗漏率；
- 无依据推断率；
- 虚假共识率；
- 边界侵犯率；
- 双方较低一侧的公平和安全评分；
- AI 草稿修改率；
- 审查器问题识别的精确率与召回率；
- P50/P95 延迟、Token、失败率和单次成功协商成本。

评测规则：

- 以房间为抽样单位，A/B 评分不能当成独立样本；
- 分开评价 AI 初稿与用户修改后的最终版本；
- 报告双方平均值之外的最低侧指标；
- 三组使用可比较的输入和 Token 预算；
- 预先确定主要指标和最低实际提升，避免只挑好看的结果。

退出条件：

- 如果多 Agent 未显著减少遗漏、曲解或虚假共识，回退到更简单架构；
- 如果审查 Agent 不能可靠识别高风险问题，不让其作为安全保证，只保留程序硬规则和明确降级；
- 如果 P95 延迟或成本超出预算，减少调用而不是隐藏等待状态。

### M6：全链路验证与测试发布

验证清单：

- 领域逻辑和状态机单元测试；
- RLS、RPC 和 migration 测试；
- 模型响应 schema、超时和失败测试；
- 幂等、并发、乱序和属性测试；
- H5 真实页面视觉与交互验证；
- 微信开发者工具编译和关键流程验证；
- 类型检查、lint、H5 构建、mp-weixin 构建；
- 代码质量 review，无 Critical 或 Required 问题；
- 日志和错误平台检查，确认没有 token 或私密原文泄露。

发布顺序：

1. 从已同步本地 `main` 创建独立 `codex/*` worktree；
2. 功能分支实现、测试、构建和 review；
3. 合并到本地 `main` 并复核；
4. 推送 GitHub `main`，确认本地、远端和 GitHub 提交一致；
5. 从 GitHub `main` 的干净检出部署测试环境；
6. 验证线上 build 与 GitHub commit 对应；
7. 不部署生产环境，除非收到单独明确授权。

## 4. 建议开发拆分

为降低合并风险，每个里程碑继续拆成可独立评审的纵向变更：

| 变更 | 内容 | 是否可能涉及 schema |
| --- | --- | --- |
| A | 产品规格、状态机与 Agent schema 契约 | 否 |
| B | 表达版本、确认、任务与 RLS 基础 | 是，必须先评审 |
| C | 路径选择和单方理解流程 | 取决于 B |
| D | 双方汇合、共识和审查循环 | 是 |
| E | 行动选项、暂停与结束 | 可能 |
| F | 离线评测工具和数据集 | 否，测试数据不得使用真实用户数据 |
| G | 全链路测试和测试环境发布 | 否 |

## 5. 首个工程任务包

M0 通过后，第一个工程任务不是直接接三个 Agent，而是提交 M1 技术设计包：

1. 当前表、RPC、RLS 和房间状态盘点；
2. 新旧状态映射；
3. 最小 schema 草案；
4. 字段级权限矩阵；
5. 模型任务和结果版本绑定协议；
6. migration、历史数据兼容和回滚计划；
7. 单元、RLS、并发和故障测试设计；
8. 成本与延迟预算草案。

技术设计包获批后，再实施 migration 和 M2 单方纵切。

## 6. 默认产品决策

为避免开发中反复停顿，首版采用以下默认值，后续可以在产品评审中修改：

- 默认推荐非暴力沟通，但始终展示其他路径；
- 理解 Agent 最多提出一个澄清问题；
- 审查不通过后最多自动修订一次；
- 用户可以跳过 AI，手动填写结构化表达；
- 一方暂停时不要求填写原因；
- 共同理解必须双方确认后才能生成行动选项；
- 行动选项可以全部拒绝；
- 不做影子运行，不上线生产；
- 首版不增加主 Agent、自由辩论或多人房间。
