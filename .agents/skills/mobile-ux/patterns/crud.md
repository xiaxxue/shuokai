# Pattern: CRUD (Create / Read / Update / Delete)

「何かを記録して見返すアプリ」の骨格。読書記録・家計簿・在庫管理・習慣トラッカーなど、AIに依頼される個人向けアプリの大半はこの形に落ちる。

## いつ使うか

ユーザーが自分でデータを追加し、一覧し、編集・削除するアプリ。

## 設計手順

1. **主オブジェクトを1つ決める** — ユーザーが「増やしたい」と思う対象（本、支出、在庫品）。複数のオブジェクトを対等に並べない。主オブジェクト以外は属性か関連として扱う。
2. **主タスクを判定する** — CRUDの4つは対等ではない。多くのアプリで頻度は **Create ≫ Read > Update > Delete**。家計簿は入力が主タスク、読書記録は「既に読んだか確認する」検索が主タスクのこともある。頻度順を先に決めると画面構成が決まる。
3. **Create の導線を最短にする** — 主タスクがCreateなら、起動から入力完了までのタップ数を数える。3タップを超えるなら設計を疑う。入力欄は必要最小限（FORM-003）、既定値を最大限使う（日付＝今日、カテゴリ＝前回値）。
4. **一覧の並び順と検索を決める** — 「最後に追加したものが上」が既定として最も無難。件数が増えたときの検索・絞り込みは、初期の件数がゼロでも後から追加しやすい位置に置く。
5. **一覧行の情報を決める** — ユーザーが探すときの手がかりを先頭に置く（LIST-002）。すべての属性を並べない。
6. **編集と削除の導線を決める** — 詳細画面からの編集が基本。行からの直接削除はスワイプ単独にしない（LIST-003）。削除は DESTR-001（Undo優先）。
7. **状態を設計する** — 特に初回の空状態（STATE-004）。CRUDアプリの第一印象は「まだ何もない画面」であり、ここが最重要画面と言ってよい。

## 典型的な画面構成

```text
一覧（タブ or ルート）
 ├── 空状態: 「まだ〇〇がありません」+ 追加ボタン
 ├── 検索 / 絞り込み（件数が増えたとき）
 └── 行タップ → 詳細
       ├── 編集 → 入力フォーム（作成と同一フォーム）
       └── 削除 → Undo付き削除 → 一覧へ戻る
追加（FAB / ツールバー）→ 入力フォーム → 一覧へ戻り、新規項目が見える
```

## 関連ルール

FOUND-001（目的起点の設計）、STATE-001（状態網羅）、STATE-004（空状態）、LIST-001（カードの濫用禁止）、LIST-002（行の可読性）、LIST-003（行アクションの代替）、FORM-003（フィールド最小化）、FORM-006（入力保全）、DESTR-001（Undo優先）、BTN-002（主操作の可視性）。

## よくある失敗

- CRUDの4操作を対等に扱い、使用頻度の低い削除に一等地を与える
- 追加ボタンをオーバーフローメニューに隠す（BTN-002違反）
- 一覧行に全属性を詰め込み、探すための手がかりが埋もれる
- 空状態を作らず、初回起動が真っ白になる
- 作成フォームと編集フォームを別実装にして、片方だけ検証が抜ける
