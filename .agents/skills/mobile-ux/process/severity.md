# Severity 定義

各ルールの `severity` の意味と、レビュー時の扱い。

| Severity | 定義 | レビュー時の扱い |
|----------|------|----------------|
| **critical** | ユーザーがタスクを完了できない、戻れない、データを失う、または重要情報にアクセスできない（致命的なアクセシビリティ欠陥を含む） | 1件でも不合格。例外なし。必ず修正 |
| **high** | タスク完了は可能だが、重大な迷い・誤操作・回復不能なエラー体験を高頻度で引き起こす | 原則不合格。適用除外には exceptions に合致する明文の理由が必要 |
| **medium** | 効率・明快さを明確に損なうが、ユーザーは自力で回復できる | 修正推奨。残す場合は理由を記録 |
| **low** | 磨き込みの問題。一貫性・余白・微細な文言 | 時間があれば修正 |
| **suggestion** | 文脈次第で改善になりうる提案 | 判断はAgentに委ねる |

## 判定例

| 事象 | Severity |
|------|----------|
| 戻る手段のない画面、閉じられないモーダル | critical |
| 削除操作に確認も取り消し手段もない | critical |
| 本文テキストのコントラスト比が 4.5:1 未満 | critical〜high（重要情報なら critical） |
| タップ領域が 44pt/48dp 未満 | high |
| エラーメッセージに原因も対処も書かれていない | high |
| 主操作のボタンがスクロールしないと見えない | high |
| フォームの必須項目が送信時まで分からない | medium |
| ボタンラベルが「実行」「OK」など結果を予測できない | medium（破壊的操作なら high） |
| リスト項目間の余白が不均一 | low |

## Severity と出典の関係

critical / high のルールは Tier A または B の出典を最低1つ持たなければならない（`scripts/validate_rules.py` が検査する）。根拠の弱い規範に高い強制力を与えないため。
