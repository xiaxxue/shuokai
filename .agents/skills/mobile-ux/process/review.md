# UX Review 手順

設計または実装に対するレビューの実行手順。レビューは**チェックリスト主導**であり、rubric の点数はチェック結果から導出する（設計判断 D-005: AI の自己採点単独ではインフレするため）。

## 手順

### 1. 適用ルールの選定

`rules/INDEX.md` を読み、レビュー対象（画面・フロー・変更差分）に適用されるルールを選定する。

**検査は severity で段階化する**（全ルール一律の全件チェックはしない。v0.1 評価で、101件全件チェックが設計文書本体の3倍以上の分量を生み、レビューが成果物を圧迫したため — D-012）。

| Tier | critical + high（51件） | medium 以下（50件） |
|------|------------------------|--------------------|
| **T1** 新規アプリ | **全件**、1件ずつ根拠付きで回答 | 対象領域のみ。違反したものだけ記録し、全件の回答表は作らない |
| **T2** 画面/フロー単位 | 対象画面に関係するもの + states/accessibility/content は常に含める | 対象領域のみ |
| **T3** 小修正 | 変更に関係するもののみ | 変更に関係するもののみ |

出力する回答表は critical/high のみ。medium 以下は「検査した領域」と「見つかった違反」だけを書く。

### 2. チェックリスト実行

選定した各ルールの `review_check` に対し、対象の具体的箇所を挙げて回答する。

```text
TOUCH-001: Yes | No | N/A
  根拠: <どの画面のどの要素を確認したか。No の場合は違反箇所と実測値>
```

規律:
- **No の回答には必ず違反箇所（画面名・要素名・実際の値）を書く。** 書けない No は再調査する。
- **Yes の回答も、critical/high ルールについては確認箇所を1つ以上挙げる。** 根拠のない全件 Yes はレビュー不成立。
- N/A は「対象要素が存在しない」場合のみ。exceptions 該当は Yes 扱いとし理由を書く。
- **設計文書に記述がない場合は Yes にしない。** 「未記述」として記録し、その意思決定が必要かどうかを判定する（必要なら No）。設計されていないものは実装されない。

### 2.5. 反証パス（自己レビュー時は必須）

自分が作った設計を自分でレビューする場合、上記だけでは違反を見逃す。v0.1 評価では、自己レビューが3アプリすべてで「critical 0 / high 0」と判定した設計のうち2件が、独立レビューで違反ありと判定された（`eval/results/REPORT.md`）。

**この節の初版は機能しなかった。** 「違反しているとすればどこか」と自由に問わせると、Agent は**自分が既に修正した論点についてだけ問いを立て**、未検査の領域には触れない。修正後の設計を独立レビューにかけたところ、自己評価 92点に対し 61点・high 3件の判定になり、反証パス9問はすべて対処済みの論点についてのものだった（`eval/results/review-habit-tracker.md`）。

そこで反証は**自由な自問ではなく、以下の決められた4つの機械的な点検**として実行する。いずれも「自分が何を見落としたか」を自分に問わず、文書の構造から未検査箇所を炙り出す形にしてある。

#### 2.5.1 要素の棚卸し（画面に置いたものが全層に伝播しているか）

各画面の構成（§8相当）に登場する**すべての要素・機能を列挙**し、それぞれが以下に現れるかを表で確認する。1つでも欠けたら、そのルールは Yes にできない。

| 要素 | フロー | 状態マトリクス | 文言 | アクセシブルネーム |
|------|-------|--------------|------|------------------|

**一度しか言及していない機能が最も危険。** 実例: 設定画面に「データの書き出し」を置きながら、フロー・状態・文言・a11y のいずれにも存在せず、その画面の loading が「読み込み待ちは発生しない」という事実に反する理由で除外されていた。

#### 2.5.2 修正の伝播（改稿でどの節が古くなったか）

設計を修正した場合、**修正した箇所を参照している他の節を列挙し、それぞれが新しい設計に更新されているかを確認する**。更新されていない節を根拠にした Yes は無効。

実例: リスト行の構成を `[−] 3/8 [＋] 名前` から「行全体が単一のタップ対象」に修正した後もアクセシビリティ節が旧構成のまま残り、自己レビューがその古い節を根拠に4ルールを Yes と採点していた。

#### 2.5.3 根拠の実在確認（引用先が現在の文書に本当にあるか）

Yes の根拠に挙げた要素・記述について、**現在の文書中の位置を特定できるか**を確認する。特定できないものは Yes にできない。

実例: 「アイコンのみの全要素の名前を定義」として挙げた一覧に、設計上は既に廃止した `＋` ボタンが含まれ、逆に実在するステッパーやセレクタが含まれていなかった。

#### 2.5.4 「空」「無効」「対象外」の**原因**を数える

空状態・無効状態について、**それが発生する原因を画面ごとに列挙する**。原因が2つ以上あるなら、文言とCTAも原因の数だけ必要になる。「0件」だけを空状態と考えない。

原因の例: 一度も作られていない / フィルタや検索条件に一致しない / 日付や曜日の条件で対象外 / 権限がない / 同期がまだ / アーカイブ済み。

実例: 曜日指定と開始日を自ら設計しておきながら、最頻画面の空状態を「習慣0件」の1種類しか用意せず、登録済みユーザーに「まだ習慣がありません／習慣を追加」という誤った理由とCTAが出る設計になっていた。

#### 2.5.5 未検証を明示する

実測が必要な項目（コントラスト比、200%拡大時のレイアウト、ヒット領域の実寸、読み上げ順、インセットの被り、予測型バックの挙動）は、設計段階では Yes ではなく **「未検証」** として記録し、実装後に再検査する。

**同じセルの中で「実測は実装後」と書きながら Yes にしない。** 実例: SPACE-002 / TYPE-001 / AND-002 の3件が、根拠欄に「実測は実装後に行う」と自ら書いたうえで Yes と判定されていた。あるルールを未検証にしたなら、同じ対象を検査する他のルールも未検証になる。

#### 2.5.6 見落とされやすい領域を再確認する

v0.1 評価で条件を問わず脱落した領域。

- SPACE-001 / AND-002 — セーフエリアとインセット（特に Android の edge-to-edge 強制）
- A11Y-003 — スクリーンリーダーの読み上げ順序
- JA-003 — 日本語入力の全角/半角の正規化（日本語アプリの場合）

---

**自己レビューの PASS は「明白な違反を潰した」ことを意味するに留まる。** 実測で、自己レビューと独立レビューの判定は毎回乖離している（100→85、96→93、93→72、92→61）。上記の点検を加えても乖離は消えていない。

**T1（新規アプリ）および外部に出す成果物では、独立したセッションによるレビューを行うこと。** 自己レビューはその前段の絞り込みとして使う。

### 3. 違反の集計

severity 別に No の件数を集計する。

### 4. Rubric 採点

各カテゴリの点数は、そのカテゴリに属するチェック結果を根拠に採点する。根拠のない満点は禁止。

| Category | 配点 | 主な根拠となるルール群 |
|---|---:|---|
| User goal / task completion | 20 | FOUND, patterns/ |
| Information architecture | 15 | FOUND, NAV |
| Navigation | 15 | NAV, IOS/AND |
| Interaction / touch usability | 10 | TOUCH, BTN, FORM |
| UX Writing | 10 | WRITE, JA |
| Feedback / Error handling | 10 | STATE, FORM, FOUND |
| Accessibility | 10 | A11Y, COLOR, TYPE, TOUCH |
| Platform conventions | 5 | IOS, AND, NAV |
| Visual consistency | 5 | SPACE, TYPE, COLOR |
| **Total** | **100** | |

採点目安（カテゴリごと）: 違反なし = 満点、medium 違反あり = 60-80%、high 違反あり = 30-60%、critical 違反あり = 0-30%。

### 5. 合格判定

```text
合格 =  critical 違反 0
     かつ high 違反 0（または各違反に exceptions 準拠の明文理由）
     かつ rubric 合計 >= 80
```

点数が 80 以上でも critical/high が残っていれば不合格。

### 6. 不合格時の修正ループ

```text
違反を severity 降順に並べる
↓
critical → high の順に修正（medium 以下は任意）
↓
修正した箇所に関係するルールのみ再チェック
↓
再判定（最大3周。3周で収束しない場合は設計自体を1段階戻って見直す）
```

## レビュー結果の出力形式

```markdown
## UX Review Result

- 対象: <画面/フロー/差分>
- Tier: T1 | T2 | T3
- チェック実行数: N (Yes: n1 / No: n2 / N/A: n3)

### 違反一覧（severity 降順）
| Rule | Severity | 違反箇所 | 修正方針 |
|------|----------|---------|---------|

### Rubric
| Category | Score | 根拠 |
|----------|------:|------|
| ... | | |
| **Total** | **NN/100** | |

### 判定: PASS / FAIL（理由）
```
